# Chotu-Gyani Backend: Complete Implementation Plan

*Your business. Your language. Your AI.*

This plan turns the master prompt into an executable build. It is ordered so the golden path works first, then widens. Every phase ends with a gate: a command whose real output must be pasted into `docs/implementation-status.md`.

**Golden path (the one thing that must work):** voice or text request → validated intent → real customer/invoice lookup → pending-action preview → explicit confirmation → persisted reminder → audit record → dashboard update.

## 1. Goals, non-goals, tiers

### Goals

- A shopkeeper can speak or type in Hindi, English, or Hinglish and manage customers, invoices, dues, and reminders.
- Every business-changing action is previewed and explicitly confirmed.
- Tenant isolation, idempotency, and auditability are enforced by the backend and the database, not by the LLM.
- Runs end to end locally with explicit mock providers and no real credentials.

### Non-goals (do not build)

- Microservices, Kafka, Kubernetes, vector databases, multi-agent frameworks.
- Real WhatsApp/SMS/telephony delivery (stub only until a provider is chosen).
- Payments processing. The system records payments; it never moves money.
- Free-form SQL or code generated by the LLM.

### Priority tiers

| Tier | Scope |
| --- | --- |
| **P0 golden path** | register/login/me, business create/me, customers, invoices (+payments read), reminders, conversations + messages, actions confirm/cancel, dashboard summary, health/ready, audit-logs read, mock LLM/STT/TTS |
| **P1 demo quality** | agent generate/save/test/activate, audio transcribe/speech/message-audio, idempotency, expiry, RBAC matrix, real LLM provider, usage limits, seed script, payment commitments |
| **P2 stretch** | Celery delivery, refresh/logout, invitations and member management, CSV import, Google Sheets, export/deletion, forgot-password, provider health |

## 3. Architecture

One FastAPI modular monolith. Layers:

- **api/**: thin route handlers. Parse input, call a service, shape the response.
- **services/**: business logic and transactions.
- **repositories/**: only where queries are complex (customer fuzzy search, dashboard aggregates, balance calculation). Simple CRUD uses SQLAlchemy directly in services.
- **providers/**: `llm`, `stt`, `tts` interfaces with `mock` and real adapters, chosen by config.
- **core/**: settings, security, errors, logging, rate limiting.
- **workers/**: reminder poller (P0/P1), Celery tasks (P2).

### Request flow

1. Middleware assigns a request ID and starts a timer.
2. Auth dependency validates the JWT, loads the user.
3. Business dependency reads `X-Business-ID`, verifies membership, returns `(business, member, role)`.
4. Permission dependency checks the role against the matrix.
5. Route calls a service; the service opens a transaction.
6. Errors map to the standard error envelope; no stack traces leak.

### Response envelopes

Success: `{ "data": ..., "meta": {} }`. Error: `{ "error": { "code", "message", "details" } }`. Lists carry `meta.page`, `meta.page_size`, `meta.total`.

## 5. Data model

All business-owned tables carry `business_id` (indexed, FK). All have `id uuid`, `created_at`, `updated_at` unless noted.

- **users**: email (unique, citext), password\_hash, name, is\_active.
- **businesses**: name, timezone, default\_language, currency (`INR`), archived\_at.
- **business\_members**: business\_id, user\_id, role; unique (business\_id, user\_id).
- **customers**: business\_id, name, name\_normalized, phone\_e164, email, external\_ref, notes, archived\_at. GIN trigram index on `name_normalized`; index on (business\_id, phone\_e164) (not unique).
- **invoices**: business\_id, customer\_id, number (unique per business), total\_paise, issued\_on, due\_on, status (`open`, `paid`, `void`), description. CHECK total\_paise > 0.
- **payments**: business\_id, invoice\_id, amount\_paise, paid\_on, method, source\_action\_id (unique, nullable). CHECK amount\_paise > 0.
- **payment\_commitments**: business\_id, customer\_id, invoice\_id (nullable), promised\_amount\_paise (nullable), promised\_on, status (`open`, `kept`, `broken`, `cancelled`), source\_action\_id (unique, nullable).
- **reminders**: business\_id, customer\_id, invoice\_id (nullable), scheduled\_at (UTC), channel, status, creation\_source, delivery\_attempts, last\_error, completed\_at, source\_action\_id (**unique**).
- **agents**: business\_id, name, description, language, instructions, enabled\_tools (jsonb), knowledge\_sources (jsonb), status (`draft`, `active`, `archived`), config\_version.
- **conversations**: business\_id, agent\_id, user\_id, language, state (jsonb, holds `awaiting`), is\_test.
- **messages**: conversation\_id, role, content, intent (jsonb), tool\_metadata (jsonb), language. No chain-of-thought.
- **pending\_actions**: business\_id, conversation\_id, user\_id, type, payload (jsonb), preview (jsonb), status, expires\_at, confirmed\_by, result (jsonb), error.
- **action\_logs** (audit): business\_id, actor\_user\_id, action\_type, entity\_type, entity\_id, outcome, metadata (safe jsonb), created\_at. Append-only.
- **idempotency\_keys**: business\_id, user\_id, route, key, request\_hash, response\_body, status\_code, created\_at; unique (business\_id, user\_id, route, key).
- **usage\_records**: business\_id, metric, period, count; unique (business\_id, metric, period).
- **integrations** (P2), **refresh\_tokens** (P2), **password\_resets** (P2).

### Action state machine

`pending_confirmation → processing → completed | failed`; `pending_confirmation → cancelled | expired`. No other transitions. Enforced by conditional `UPDATE`, not by application checks alone.

## 6. The assistant pipeline

### Contract

1. **Normalize** input text. For audio, STT runs first and the result enters the same function as typed text.
2. **Intent extraction**: one LLM structured-output call returns `Intent{ type, entities, confidence, missing_fields[] }`, validated by Pydantic. Allowed types map one-to-one to the tool allowlist plus `clarify`, `smalltalk`, `unsupported`.
3. **Relative dates**: the LLM emits `{ "relative": "next_monday", "time": "10:00" }` or an absolute date; `utils/dates.py` converts using the business timezone and rejects past times.
4. **Number words**: `utils/numbers.py` parses "do lakh", "paanch hazaar", "dedh sau", "1.5 lakh" into paise. The LLM may extract the phrase; code computes the value.
5. **Entity resolution**: exact phone match first, then `pg_trgm` similarity on `name_normalized` (with transliteration normalization: lowercase, strip vowels variants like `aa/a`, `v/w`). More than one candidate above the threshold returns a clarification with numbered options.
6. **Clarification state**: stored in `conversations.state.awaiting = { slot, candidates[], intent_snapshot }`. The next turn first tries to resolve the awaiting slot ("the second one", "Ramesh Gupta", "2") before running fresh intent extraction.
7. **Missing fields**: amount or date missing means ask a question; never guess.
8. **Permissions**: effective tools = agent `enabled_tools` ∩ role permissions ∩ global allowlist.
9. **Execute**: read tools run immediately. Write tools create a `pending_action` with a human-readable preview and `expires_at`.
10. **Respond** in the user's language: fixed phrases (confirmations, errors, clarifications) come from a template layer in `utils/i18n.py` (`en`, `hi`, and Hinglish variants); the LLM only writes free-form answers.

### Prompt-injection defenses

- Tool results, customer notes, invoice descriptions, and imported rows are wrapped in `<data>` delimiters and the system prompt states they are data, never instructions.
- Free-text fields are never concatenated into the intent prompt unwrapped.
- LLM output only selects from the allowlist and fills validated schemas; it cannot name arbitrary tools, ids it was not given, or SQL.
- Agent instructions are untrusted: they can shape tone and focus, never permissions.
- An injected string in a customer note is a test case (see section 11).

## 7. Tool registry

Each tool is a class with: `name`, `description`, `input_schema` (Pydantic), `kind` (`read`|`write`), `min_role`, `requires_confirmation`, `audit_event`, and `run(ctx, input)`.

| Tool | Kind | Min role | Confirmation |
| --- | --- | --- | --- |
| `search_customers` | read | member | no |
| `get_customer_balance` | read | member | no |
| `get_invoice_details` | read | member | no |
| `list_overdue_invoices` | read | member | no |
| `list_customer_reminders` | read | member | no |
| `get_dashboard_summary` | read | member | no |
| `schedule_reminder` | write | member (propose), admin (confirm) unless business setting relaxes | yes |
| `record_payment_commitment` | write | member (propose) | yes |
| `record_payment` | write | owner/admin (confirm) | yes, always |

Execution of a confirmed action re-resolves and re-validates every referenced customer, invoice, amount, and date inside the transaction before mutating.

## 8. Concurrency and idempotency

- **Confirm** runs: `UPDATE pending_actions SET status='processing', confirmed_by=:u WHERE id=:id AND business_id=:b AND status='pending_confirmation' AND expires_at > now() RETURNING *`. Zero rows returns 409 (already handled) or 410 (expired) after a follow-up read scoped to the business; a foreign business id returns 404.
- The mutation and the move to `completed` happen in one transaction with the audit insert.
- **Hard guarantee**: unique constraints on `reminders.source_action_id`, `payments.source_action_id`, `payment_commitments.source_action_id`. A double execution fails at the database even if code is wrong.
- **Idempotency-Key** on write endpoints: first request stores `(request_hash, response, status)`; same key and hash replays the stored response; same key with a different hash returns 422. Keys expire after 24 h.
- **Concurrency test**: 50 parallel confirms leave exactly one reminder and one `completed` transition.

## 9. Security checklist

- Argon2id hashing; password policy; login and register rate limits (Redis if present, in-memory fallback in dev).
- JWT validation with `exp`, `iss`, `aud`; secrets from env; production startup fails on insecure defaults.
- Every query filters by `business_id` from the verified membership, never from the body.
- 404 (not 403) for resources in other tenants.
- CORS limited to `FRONTEND_ORIGINS`.
- Audio validation: magic bytes, MIME, size, duration; raw audio is not persisted.
- External calls use `httpx` with timeouts and bounded retries.
- Logs carry request ID, route, status, latency, provider latency, intent type; they do not carry message text, transcripts, tokens, or secrets.
- Audit log is append-only and never stores credentials.

## 10. Voice and multilingual

- Interfaces: `SpeechToTextProvider.transcribe(audio, language_hint) -> Transcript{text, language, confidence}` and `TextToSpeechProvider.synthesize(text, language, voice) -> AudioResult`.
- Providers: `mock` (deterministic, clearly labelled in responses and `/audio/providers`), `gnani` (adapter built only from official docs and supplied credentials; otherwise a marked skeleton that raises `ProviderNotConfigured`).
- The audio message endpoint transcribes, then calls the same `process_user_message()` used by text. A test asserts identical pipeline output for equal transcripts.
- Language handling: store `language` on conversation and message; respond in the user's detected language; Hinglish (Roman script Hindi) is treated as `hi-Latn` and answered in Hinglish templates.
- Fixed-phrase templates exist for: clarification, preview, confirmation, cancellation, expiry, not found, permission denied, provider unavailable.

## 11. Testing and evals

### Infrastructure

- `docker compose` Postgres for tests; per-session schema from Alembic migrations (this also verifies migrations); per-test transaction rollback or truncate.
- Mock providers by default; no real keys required.

### Suites

- **Unit**: password hashing, balance calculation (partial payments, voided invoices), date resolution (IST, month ends, "agle somvar"), number-word parsing, intent schema validation, tool allowlist, state transitions, permission matrix (every role × every tool/route).
- **API**: auth, business, customers, invoices, reminders, conversations, agents, actions, dashboard, pagination and filters.
- **Security**: cross-tenant read/write for every resource returns 404; member cannot confirm `record_payment`; double confirm yields one effect; expired action rejected; unknown tool rejected; LLM output cannot skip confirmation; commitment never changes payments or invoice status; injected note text does not alter tool selection.
- **Concurrency**: 50 parallel confirms.
- **E2E golden path**: register → business → seed customer and unpaid invoice → "schedule a reminder" → preview → confirm → reminder row exists → second confirm → still one reminder → audit row exists → dashboard shows it.

### LLM evals

`tests/evals/utterances.yaml` with about 40 cases across English, Hindi, and Hinglish covering: balance queries, overdue counts, reminders with relative dates, amounts in number words, ambiguous names, follow-up turns, unsupported requests, and injection attempts. Each case lists the expected intent type, resolved entities, and missing fields. A runner prints intent accuracy and entity accuracy per language. Set the target before running (suggested: intent ≥ 90%, entities ≥ 85% on the real LLM; 100% on the mock).

## 12. Phased build with gates

### Phase 0: Foundation (half a day)

- Inspect repo and Git status; record findings in `docs/implementation-status.md`.
- Write `AGENTS.md` (invariants, pinned decisions, non-goals), `docs/decisions.md`, and `docs/spec/*`.
- `pyproject.toml` with `uv`, Ruff, pytest; `docker-compose.yml` (Postgres, Redis); `.env.example`; settings class; app factory; error handlers; request-ID middleware; `/health`, `/ready`.
- **Gate**: `docker compose up -d && uv run alembic upgrade head && curl -s localhost:8000/ready` returns 200; `uv run ruff check .` clean.

### Phase 1: Walking skeleton (golden path)

- Migrations for all P0 tables.
- Auth (register, login, me), business create/me, membership dependency.
- Customers and invoices (create, list, get), payments read, balance calculation.
- Reminders (create, list, get, cancel) with the unique `source_action_id`.
- Tool registry with all read tools plus `schedule_reminder`.
- Mock LLM that deterministically maps fixture utterances to intents.
- Conversations and messages, pending actions, confirm and cancel, audit log, dashboard summary.
- **Gate**: `uv run pytest tests/e2e/test_golden_path.py -v` passes against real Postgres; output pasted.

### Phase 2: Harden the core

- Permission matrix and tests for every cell.
- Tenant-isolation tests for every resource.
- Idempotency table and `Idempotency-Key` handling.
- Action expiry and expiry sweep.
- 50-way concurrent confirm test.
- Pagination, filters, and list endpoints for invoices, reminders, actions, conversations.
- **Gate**: `uv run pytest tests/security tests/concurrency -v` all green.

### Phase 3: Voice

- STT/TTS interfaces, mock providers, audio validation, `/audio/*` endpoints, audio message endpoint using the shared pipeline.
- Gnani adapter only with verified docs and credentials; otherwise leave the skeleton and document what is missing.
- **Gate**: parity test (text vs audio with equal transcript) passes; oversized and wrong-type audio rejected.

### Phase 4: Agents

- Generation service (text and audio share it), Pydantic validation, tool allowlist, size limits.
- Agent CRUD, test dry-run (forces `dry_run`, no business writes), activate and deactivate with revalidation.
- **Gate**: a generated config containing an unknown tool or SQL-like instructions is rejected; generation never auto-activates.

### Phase 5: Real LLM and evals

- Real provider adapter (structured output, timeout, rate-limit handling, safe errors).
- Eval set and runner; iterate on prompts until targets are met.
- **Gate**: printed score table meeting the pre-set targets.

### Phase 6: Background work and limits

- Reminder due-poll (single scheduler, row-locked with `FOR UPDATE SKIP LOCKED`), delivery stub that records attempts and never claims delivery, retries with exponential backoff and a cap.
- Expiry job, usage counters and quota responses (429).
- Seed script (idempotent, synthetic data, two customers sharing a first name).
- **Gate**: poller test shows one attempt per due reminder under two concurrent workers.

### Phase 7: Stretch (only if time allows)

Refresh and logout, invitations and member management, payment-commitment CRUD polish, CSV import with preview and row errors, Google Sheets OAuth, export and deletion, forgot-password, Celery/Redis delivery, provider health.

## 15. Agent working method

Split the prompt into files so the agent keeps context:

- **`AGENTS.md`** (one page): pinned decisions, invariants (confirmation required for writes, tenant scoping, no unverified claims, money in paise), non-goals, and the rule to paste real command output.
- **`docs/spec/*.md`**: API, data model, tools, pipeline (sections 3 to 10 above).
- **One short prompt per phase**: "Implement Phase N from `docs/plan.md`. Do not start Phase N+1. Finish by running the gate command and pasting its output into `docs/implementation-status.md`."

Rules:

- Commit after every phase with the gate output in the message or status file.
- `docs/implementation-status.md` is a table: feature, status, verified by (command and output).
- Never mark anything done without a command that proves it.
- If a credential or doc is missing, ship the mock and document the gap; never invent provider endpoints or fields.

## 16. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Scope creep into P2 before the golden path works | Tiers and gates; Phase 1 gate blocks all later work |
| Hinglish transcripts mis-resolve names | Transliteration normalization, trigram threshold tuning, clarification fallback, eval cases |
| LLM returns malformed or hostile output | Pydantic validation, allowlist, wrapped data, retry once then safe error |
| Duplicate reminders | Unique `source_action_id`, conditional update, idempotency table, concurrency test |
| Provider outage during demo | Mock providers switchable by config, clearly labelled |
| Gnani API details unknown | Skeleton plus mock; adapter only from verified docs |
| Test false confidence | Real Postgres, evals with measured scores |

## 17. Definition of done (MVP)

1. Register, authenticate, create a business; data is isolated between businesses.
2. Customers and invoices can be created and queried; balances computed from records.
3. Text and audio requests share one pipeline and produce validated intents.
4. Every write requires confirmation; duplicates cannot repeat an effect.
5. Reminders persist, are audited, and appear on the dashboard; none are reported as delivered by the stub.
6. Agents can be generated, reviewed, saved, tested, and activated; malicious configs are rejected.
7. A fresh database initializes from migrations; tests pass against real Postgres; Ruff is clean.
8. The app runs locally on mock providers with no credentials, and the status doc lists what needs real credentials.
9. The demo script in section 14 passes as an automated test.
